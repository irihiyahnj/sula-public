本轮用户要求对项目提出看法和优化建议；以下为评估与建议，不代表已经采纳的实现决策。

核心判断：Sula Vector 的价值在于让项目的判断理由、证据和未完成方向跨会话存活。纯渲染、项目自包含、judgment/evidence/direction 分离值得保留。下一阶段优先兑现既有可靠性承诺，并以真实交接效果衡量收益。

建议的第一优先级是统一追加写入的安全边界。note.py 的存在性检查与 write_text 分离；在临时目录固定时间并控制并发交错，两次成功调用仅留下一个片段。verifier-shell.py 对同一目标在同一秒直接写同一路径，也会覆盖前一次结果。应采用底层文件系统的排他创建与冲突重试，并设计完整内容的安全发布，保持片段身份与时间规则一致；不引入调度器或旁路状态目录。跨设备的唯一命名与捕获顺序还需单独定义，排他创建只解决同一文件系统的竞争。

证据关系必须先解析再用于判定。render.py 的 doctor 没有核验 explains/explained_by 的完整性，explanation_map 却直接用其消除缺口；一个不存在的 explained_by 目标即可令缺口不再出现。应统一检查关系目标与其语义，只有存在且合适的判断或方向才能认领捕获。

展示筛选不应重算出相反的完成状态。当前 view_goals(filtered) 会在 --kind goal 排除验证证据后把已完成目标显示为未完成。应先在完整片段集合上解析闭合、替代和解释关系，再筛选展示对象；历史截至时刻的查询另行明确语义。

捕获应诚实呈现覆盖程度。witness.py 对超过 50 MiB 的文件仅以大小充当摘要，相同大小的内容修改不会产生 delta。视频等大文件项目需要真正的流式或分块内容校验；如选择只观察元数据，必须在证据中标明，不能据此声称内容未变。宿主的完成流程应先完成捕获再运行纯 doctor；结构完整、已观察到的状态和此刻工作区状态应可区分。

读取优化应保持完整审计能力：用片段声明作用域和复核条件，显式重述或替代过时判断；完整 boot 保留，另以查询视图组织任务相关的判断及其证据链，并保留全局约束和未闭合风险。不要以最近 N 条截断恢复旧问题，也不建立第二套状态真相。

验证策略建议从测试数量转向不变量：并发 N 次追加保留 N 份内容、显示筛选不改变对象状态、无效解释关系不打开完成门、相同大小的大文件修改可见。再用代码、文档、视频素材三个真实项目比较交接找回理由的正确率、漏记率和读取成本，决定后续功能投入。
