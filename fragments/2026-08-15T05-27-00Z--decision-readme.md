README 此前是 v1.0 时代的文案叠加若干次补丁：仍写着「What v1.0 gives any project」「推荐路径是 v1.1」，缺 unexplained/decay 两个视图、缺 explains/explained_by/governs/broken_ref 四个字段、缺门禁与共用 verifier 机制，更新章节还有一处我自己造成的列表断裂。作为公开主页，它描述的不是现在这个项目。

重写为完整说明：23 个章节带目录，覆盖约定、片段格式、全部 frontmatter 字段、全部视图、doctor 全部问题码与两条 append-only 修复路径、机械捕获与四种宿主触发、三格分工、boot 契约、Tier A–E 全文、skills 契约、信任模型、substrate、明确排除项、仓库结构、验证证据、版本策略、发布史、文档索引。锚点与内部链接已自检（23 条目录 0 断链，19 条本地链接 0 失效）。

两个非常规的选择：

一、把「诚实评估」写进首页，包括价值有条件的四条（收益随寿命放大、上限卡在作者诚实、代码仓库的边际价值低于文档型项目、v1.2 成熟度有限）和一句「代码不是值钱的部分」。理由：一个以诚实记录为论点的项目，主页夸大即自我否证。同时明确写出「不承诺支持窗口，长期支持是开发目标而非承诺」——这是操作者本轮的明确立场。

二、把三件「不可表达」与其余「有工具辅助的纪律」在首页就分开列。功能清单会让读者以为所有条目都是物理约束，实际只有三件是：错误 id/时间戳、悬空引用、未被发现的缺失理由。

脱敏范围仅限可编辑文件：README 与 RELEASE-NOTES 里的私有项目代号、"on this device" 一类设备指称已替换为中性表述；已核验非 legacy、非 fragments 的全部受版本控制文件里不再含私有项目名、客户名、人名或 home 绝对路径。

片段里的同类信息未处理，也无法在本约定内处理：fragments/ 有 7 处私有项目代号、8 处 home 绝对路径、5 处客户机构名、4 处人名，且已随 v1.1 公开。B1/E3 禁止编辑或删除既有片段，唯一的移除手段是重写 git 历史并强推——那会同时销毁只追加这一性质的可证性，属于必须由操作者决定的破坏性远端操作。本片段把这个状态记为已知且未解决，而不是让它无人知晓。
